# ADR-0018: Модель розкладу — правила, разові заняття, винятки

**Статус:** Accepted, 2026-09-28
**Спирається на:** рішення dev-setup-плану «розклад — час стіни: день тижня + час, tz із `schools.tz`».

## Контекст
Потрібні регулярні заняття й разові; перенесення й скасування одного заняття без зміни правила; відновлення скасованого; зміна розкладу групи з дати наперед. Відмітки й оплати мусять посилатися на конкретне заняття.

## Рішення
- **Правило** = група + **один** день тижня + час початку + тривалість (за замовчуванням 60 хв) + `valid_from` + `valid_to NULL`. Група «пн, ср 17:00» — два правила; UI показує їх разом.
- **Разове заняття** — окремий запис: група + дата + час + тривалість, свій id.
- **Ідентичність заняття (`LessonRef`)**: регулярне — `(rule_id, original_date)`; разове — `one_off_id`. На `LessonRef` посилаються відмітки, списання, винятки, сповіщення.
- **Винятки** — події з `LessonRef`: перенесено (нова дата/час), скасовано, відновлено. Діє останній за `seq`. **Перенесене заняття зберігає свою ідентичність** (оригінальну дату): відмітка на новій даті посилається на той самий `LessonRef`.
- **Зміна розкладу групи з дати D** = закрити старе правило (`valid_to = D − 1`) + нове правило з `valid_from = D`. Правило ніколи не змінюється «на місці»; минулі заняття лишаються за старим правилом. Припинити заняття групи = лише закрити правило.
- **Сітка тижня рахується при читанні** з правил + винятків + разових занять; заняття наперед не матеріалізуються.
- Час стіни → UTC — у момент обчислення конкретної дати (`zoneinfo`, `schools.tz`). Факти (відмітки, події) — `timestamptz` UTC, як і було.

## Альтернативи
- **RRULE (iCalendar)** — потужніше, ніж потрібно; складні правила = складні винятки.
- **Матеріалізувати майбутні заняття рядками** — ламається при зміні правила, потребує джоби «горизонту» і прибирання.
- **Правило з кількома днями тижня** — винятки й зміни для одного дня ускладнюються; «один день = одне правило» простіше.

## Наслідки
- M4 (відвідування) і M5 (списання) залежать від `LessonRef`.
- Винятки для дат старого правила після `valid_to` ігноруються; UI попереджає, якщо зміна розкладу зачіпає вже перенесені/скасовані майбутні заняття.
- Тести: переходи на літній/зимовий час (Europe/Kyiv, остання неділя березня/жовтня); ідентичність перенесеного заняття; зміна правила посеред тижня; повторне перенесення.

## Для Claude Code
- Ніколи не зберігати заняття наперед і не робити UPDATE правила — лише закрити + нове.
- Винятки й відмітки — завжди через `LessonRef`, ніколи через дату/час, що відображається.
- Час правила — `time` + tz закладу, не `timestamptz`.
