# ADR-0013 — Ручні реліз-теги як псевдоніми збудованих образів

Статус: accepted (2026-09-20). Уточнює ADR-0010 (формат тегу образу).

## Контекст
main деплоїться безперервно: кожен merge → образ `:<sha12>` + `:latest`
→ автодеплой (release.yml). Для комунікації («у 0.2.0 з'явився екран
оплат») потрібні людські версії — без зміни моделі безперервного
деплою. Те саме рішення вже працює в lozar (його ADR-0011); CI/CD двох
проєктів свідомо тримаємо однаковими.

## Рішення
Реліз = просування, не пересборка. Git-тег `vX.Y.Z` запускає
tag-release.yml, який через `docker buildx imagetools create` додає тег
`X.Y.Z` до ТОГО САМОГО digest у GHCR, що вже пройшов CI і працює на VPS.
Тегувати можна лише коміт з main, ПІСЛЯ зеленого Release (інакше образу
`:<sha12>` не існує і воркфлоу гучно падає — бажана поведінка).
Тег образу — перші 12 символів GITHUB_SHA (ADR-0010 казав «тег =
GITHUB_SHA»; це той самий коміт, коротший для ручного відкату).
Нумерація: 0.x — увесь шлях до першої школи поза design-partner;
v1.0.0 — коли нею користується хтось, кого ми не знаємо особисто.
Версія в pyproject.toml від тегів не залежить.

## Альтернативи (відкинуті)
- Пересборка по тегу: артефакт перестає бути байт-у-байт тим, що
  тестувалось і вже задеплоєне.
- Версія з git (dynamic versioning у pyproject): не потрібна, поки
  version ніщо не споживає.

## Наслідки
- Деплой/відкат конкретної версії на VPS:
  `IMAGE_TAG=<X.Y.Z або sha12> docker compose -f docker-compose.prod.yml up -d`.
- Тег назавжди вказує на перевірений digest; історія релізів = git-теги.
- `:latest` і останній людський тег можуть розходитись (latest — завжди
  останній main); це очікувано.

## Для Claude Code
Не додавати checkout/збірку у tag-release.yml — лише imagetools create.
Не «чинити» падіння на відсутньому `:<sha12>` — це запобіжник. Реліз —
це git-тег; version у pyproject.toml заради релізу не чіпати.
