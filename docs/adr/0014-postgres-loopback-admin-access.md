# ADR-0014 — Адмін-доступ до prod-Postgres: лише loopback сервера

Статус: accepted (2026-09-20). Виняток з ADR-0005 (пункт «published
ports має лише caddy»).

## Контекст
ADR-0005: у prod-compose published ports має лише caddy. Але дивитися
events/jsonb очима на проді треба (підтримка design-partner, перевірка
restore, розбір інцидентів), і робити це зручно з DBeaver, а не з psql
у контейнері. У lozar те саме вирішено публікацією порту Postgres на
loopback сервера + ssh-тунель; hardening двох проєктів свідомо тримаємо
однаковим.

## Рішення
Сервіс postgres у docker-compose.prod.yml публікує порт ТІЛЬКИ на
loopback VPS: `ports: ["127.0.0.1:5432:5432"]`. Ззовні він недосяжний:
вхід — лише через ssh-тунель під deploy (DBeaver, вкладка SSH:
deploy@VPS → localhost:5432). ufw для цього порту НЕ відкривається.
Це єдиний виняток: усі інші сервіси, крім caddy, — без published ports.

## Альтернативи (відкинуті)
- `docker compose exec postgres psql`: працює (і лишається запасним
  шляхом), але jsonb у терміналі нечитабельний, а [К] знає DBeaver.
- Публікація на 0.0.0.0 з правилом ufw: Docker обходить ufw для
  опублікованих портів — правило не захистило б; неприпустимо.
- Окремий адмін-контейнер (pgAdmin/adminer): ще один сервіс і ще одна
  поверхня атаки за Caddy заради того, що вміє ssh-тунель.

## Наслідки
- Прив'язка `127.0.0.1:` — критична частина запису: без неї порт
  відкриється в інтернет повз ufw. Ревʼю будь-якої зміни `ports:` у
  prod-compose — обов'язкове.
- Під тунелем ходити роллю zoshyt_readonly (SELECT-only, ADR-0015):
  «дивитися очима» фізично не може писати. zoshyt_migrate — лише для
  аварійних випадків.
- На VPS порт 5432 зайнятий на loopback — другий Postgres на хості не
  ставити.

## Для Claude Code
У prod-compose `ports:` мають лише caddy (80, 443) і postgres
(`127.0.0.1:5432:5432`). Ніколи не прибирати префікс `127.0.0.1:`.
Новий published port — лише через ADR.
